# Yoyoku 图片导入、大图库与发布版性能施工方案

以 2026 年 11 月 25 日的工作区源码为基线，包含尚未提交的图库、去重、指标排序、缩略图和导出改动。沿用当前「导入 → 裁剪 → 打标 → 导出」工作流。前四节解决导入与首批可见性，第五节解决大图库和大文件浏览，第六节记录 Windows 发布包检查与修复入口。

## 1. 当前代码与测量

| 现象 | 已从源码确认的原因 | 实现入口 |
| --- | --- | --- |

| 导入过程中浏览、完成后打开图库可能停顿 | 缓存未命中的 `/thumb`、`/display` 在同步协议回调里做查库、解码和读写，使用同一个图像进程池。图库去重角标调用完整去重扫描，计算期间仍持有项目唯一数据库连接的锁。 | [`lib.rs` 的图片协议](../src-tauri/src/lib.rs#L50)、[`quality.rs` 的去重扫描](../src-tauri/src/project/quality.rs#L1431)、[`LibraryPage.tsx` 的角标刷新](../src/features/library/LibraryPage.tsx#L126) |

在当前 Windows 主机（i5-12400F、Pillow 10.4.0）对三张 3840×2160 合成噪声图分别预热 2 次、计时 7 次并取中位数。分析直接调用项目的 `op_analyze`。下面是单图、热文件缓存条件下的局部计时。

| 合成图 | 体积 | 独立读取并做 SHA-256 | 仅分析 | 分析并写 256 px 缩略图 |
| --- | ---: | ---: | ---: | ---: |
| JPEG RGB | 7.1 MiB | 20.2 ms | 122.6 ms | 131.2 ms |
| PNG RGB | 23.7 MiB | 93.5 ms | 179.7 ms | 200.7 ms |
| PNG RGBA | 31.7 MiB | 95.5 ms | 286.1 ms | 378.0 ms |

SHA-256 使用 Python 的独立流式计时，和 Rust 实际耗时有关的结论应以应用内埋点为准。合成图使用固定随机种子 897，JPEG 质量 90，PNG 压缩级别 3。计时覆盖分析函数和缩略图落盘，应用内的进程通信、并行、数据库和首屏时间仍需单独测量。`README.md`、`PROJECT_SPEC.md` 与 `docs/ACCEPTANCE.md` 记录过不同版本的缩略图策略，当前 `import_one` 明确传入 256 px 目标路径。

## 2. 先做的改动

### 2.1 复制期间计算哈希，用暂存字节分析

1. `import.rs` 先根据来源根和相对路径查已导入记录，按现有规则跳过。复制模式用打开的源文件句柄一次流式写入 `originals/` 下的任务暂存文件，同步计算 SHA-256 和字节数。记录读前、读后文件属性。在本地文件系统可用时结合文件身份识别同名替换。发现变化按 `SOURCE_CHANGED` 报告。
2. 读取结束后用哈希执行现有 `skip` / `keep` 规则。对于跨路径的精确重复，`skip` 处置自身的暂存文件，`keep` 继续创建独立图片记录、标注记录与分组归属。按哈希及最终对象路径协调并发写入。库中有现成对象时按现有保护规则确认可复用，且合并同一任务内对同一已验证对象的检验。已有内容不一致时沿用 `CONTENT_CONFLICT`，保留现场；持有暂存的候选失败时让同组候选重新竞争或进入重试，报告只把已提交代表计为成功重复项。
3. Pillow 读暂存文件执行实际解码，分析、哈希和受管理原件引用同一份字节。依然先确认静态帧数、像素上限、图像可解码、EXIF 归正尺寸和 alpha。把 `worker/main.py` 中 80 MP 和静态图限制放到实际解码前的入口检查，覆盖扫描后路径更换的情况。分析成功且接近写库时，以同一卷内的不覆盖提交发布最终内容对象。目标已经存在时复用经过验证的对象。保持现有 `originals/<hash>.<ext>` 寻址与旧项目可读性。
4. 引用模式沿用源文件路径，完整哈希读一次，分析前后核对来源状态，将消失、被替换或变化的图标为可重试错误。写库前核对实际导入模式与 `source_path` 使用的来源模式一致，测试同一目录先引用后复制和反向次序。引用内容在以后发生变化时仍沿用重新定位与导出校验流程。

唯一素材和跨盘复制优先用这条路径。预先已登记的同路径跳过项避免写入任何暂存。大量内容相同但路径各异的候选仍会暂存一次，基准需单独覆盖这一类目录，再决定是否对实测很慢的磁盘或重复比例引入额外优化。

### 2.2 短事务分批提交，图库随提交更新

1. 并行图像处理输出完整的待提交记录，由每个项目的导入写入端统一提交。准备 SQL 参数、分析、哈希、缩略图及大文件 I/O 放在数据库锁外。每个提交包含资产、初始裁剪和标注修订、目标集合归属及对应任务项检查点。首个小批 4–8 张，积攒未满时可在约 100 ms 刷新。后续从 16–32 张或 150–250 ms 的时间窗起测，同时受暂存字节和数据库锁持有时间限制。单项失败通过保存点或逐项回退隔离，任务结果按成功提交的记录计数。
2. 同一项目的导入任务串行提交时，在写入端分配排序范围并按扫描顺序使用，锁内保留最终来源路径与哈希去重复核。项目文件锁、来源归属、标签和集合写入沿用当前实现。把**最终生效的 `collectionId`** 与选项同任务一起持久化，重试按同一份输入执行。当前确认入口只覆盖内存缓存里的分组，重试从旧扫描文件读取，导入对话框后选的分组有丢失风险。恢复以已提交任务项为依据，保留结果应用侧可见，使用稳定键避免重插。
3. 提交后发送节流的 `assets:import-committed` 事件，含项目 ID、任务 ID、提交序号和累计提交量。前端首批立即消费，后续每 250–500 ms 至多刷新一次，任务结束补一次。事件只进入图库的增量刷新渠道。项目总计、集合数与任务中心按原有职责更新，避免每个批次同步触发全项目刷新和去重重算。
4. 图库保持当前筛选、排序、选中 ID、检查器焦点与滚动锚点。新记录位于当前可见范围时按有效查询插入；当前视图无匹配记录时用导入数量或新图入口反馈。`导入时间倒序`、按尺寸或按指标排序期间，新图会插入现有页中间，按查询版本重建受影响页面，以 `(排序值, ID)` 做位置恢复或游标。实现前期可复用现有查询并重查可见窗口，注意当前 `refreshLoaded` 只替换前 500 条并保留旧尾部，随后还用新偏移分页，滚动时可能出现重复 ID 或漏项。切换项目、筛选或排序后忽略旧事件和已过期的查询响应。
5. 沿用持久化任务机制确定恢复结果。以同一任务内稳定的候选标识记录已完成、待重试和失败状态，使崩溃后可以补齐缺项并保留分组。暂停停止接收新文件，正在处理的候选到达安全点后上报；取消取消待处理候选并清理所属暂存。重启区分未发布暂存、已发布但未写库和已提交对象，可复用有效对象；清理必须核对任务归属及所有数据库引用。旧扫描记录缺少新检查点时沿用来源去重和已有重试路径。

### 2.3 释放相似去重锁，保护正在浏览的图片

1. `dedupe_summary` 与完整去重扫描共用相同的分组计数语义。先用短锁读取候选摘要和回收区数量，再释放锁，把 pHash 候选匹配与组装交给后台。按 `(projectId, 去重候选版本, threshold)` 缓存结果，在导入批量结束、回收／还原以及会改变候选或推荐项的修改后合并失效。导入中显示上次角标并补一个更新状态。用户主动打开去重仍可运行当前阈值，结果完成后核对查询版本。批量提交途中避免重复扫描整个项目。
2. 图片协议使用 Tauri 已安装版本支持的异步响应，并用有界调度处理未命中请求。以 `(projectId, assetId, variant, version)` 合并并发的同图请求。生成时捕获正确的 `Project` 与裁剪配方版本，按缓存类型保存临时文件后原子发布。项目切换或新裁剪出现时避免旧任务覆盖当前版本。旧版本请求可使用与 URL 对应的缓存或返回可重试结果。对旧缓存清理继续按项目区分。参见 [Tauri 2.12.7 的异步协议方法](https://docs.rs/tauri/2.12.7/tauri/struct.Builder.html#method.register_asynchronous_uri_scheme_protocol)。
3. 给正在查看的大图、可见缩略图与裁剪预览较高优先级，导入处理在剩余容量推进，去重和指标回填安排为后台。先复用设置中的图像并发上限。优先在默认 4 并发下测 1、2、4 个有效槽位，根据当前在途像素和预估通道字节数做背压。单槽位设备按队列抢占下一项。保持网格按完整源图比例展示，使用现有 256 px 原图／处理后两种缓存键，并维持 1600 px 大图淡入、透明 WebP 和缩略图失败后的重试入口。

## 4. 基准和验收

在同一工作区基线上先测再改，依次比较第 2.1、2.2、2.3 节的效果。每次用独立临时项目，固定图片集合、并发和操作顺序，记录开发或发布构建、缓存状态、格式分布、复制／引用、源和目标磁盘。每个场景先跑 3 次完整流程并报告原始结果与中位数。单图步骤或界面交互积累足够样本后报告 P95，并附样本量。

| 指标 | 采集方式或验收点 |
| --- | --- |
| 目录预览 | 选文件或目录到预览可见。记录遍历、文件头／帧数探测、配套标注、扫描持久化四段。 |
| 首批可操作 | 确认导入到第一批事务提交、图库出现第一张卡片、第一张缩略图完成加载，分别记录时间。导入 1,000 张时可在任务运行中选中已提交图片、切换筛选、进入裁剪。 |
| 总吞吐 | 记录总秒数、每秒成功张数、每秒复制字节、完整源字节读取量、哈希／暂存／解码／统计／缩略图／数据库的用时及排队时间。复制模式的目标是每个新文件减少一次完整源读取。 |
| 应用响应和资源 | 导入中测点击筛选、滚动和打开大图，记录 P95、队列深度、项目连接锁等待以及应用和 worker 的合计峰值内存。关注同文件网络盘、USB 或 HDD 与 SSD 的差异。 |
| 回收和恢复 | 导入成功、跳过、冲突、失败、取消、崩溃和重试后核对记录、源哈希、原件与暂存。确保重新打开项目可以继续处理，暂停和取消实际结束时间可观察。 |

建议用现有 `tests/fixtures/import-set` 先核对原有功能，再生成 100／1,000／5,000 张本地测试图片。每档分别跑空项目与已有数千张图片的项目，包含 JPEG、普通和透明 PNG、高像素图、精确重复、近似重复、配套标注与损坏项，量出复制和引用两条路径。补一档高度重复、不同路径的输入，以便发现暂存写入代价。样本可包含真实分辨率分布的已许可素材，性能报告省略文件名和标注文本。

### 回归清单

- [ ] 拖放和文件选择器都可导入，新建／选择已有分组、中文与空格路径、递归开关、`.txt`／`.caption`、冲突和孤立标注报告与当前一致。失败后重试仍进原先确认的分组。
- [ ] 同路径再次导入、不同路径同内容、保留双份不同标注、原件已存在和来源在扫描后改变都有明确结果。对照源文件哈希与关闭重开后的资产记录。
- [ ] EXIF 八方向、ICC、透明 PNG、坏图、多帧 WebP/TIFF、大于 80 MP 图片分别验证；检查损坏后缀数据在工作进程验证时被报告。图库缩略图可完整显示，裁剪板、工作台及导出继续使用正确配方。
- [ ] 导入途中按宽或高／曝光／色彩丰富度／对比度／饱和度排序，切换网格与列表、项目和分组。选择、滑动多选、检查器、锚点和分页连续正确，现有图片的标注编辑可继续保存。
- [ ] 去重角标和组数一致，阈值变化、推荐保留、放大预览、回收、恢复和撤销可执行。导入进行时角标计算不能长时间占住项目数据库锁。
- [ ] 导入的图片可进入单图／批量打标、提示词统计、分组联动裁剪、质检和两种训练格式导出。透明填充开关分别对保留 alpha 的 PNG 和合成色的输出做像素对照。
- [ ] 在暂存写入、已发布原件待提交、提交后未发通知三处模拟退出，检查重试结果、回收清理及关联完整性。测试单张读取失败时其余图片仍可提交。

工程交付记录按项给出优化前后耗时与回归结果。实现顺序为采集基线、减少完整源读取、接入增量可见、缩短去重锁和图片协议等待。大图分析或网格仍占主要时间时再按第 3 节推进。

## 5. 大量图片与单图体积过大时的页面性能

### 5.1 当前页面开销与施工优先级

| 优先级 | 页面 / 现状 | 施工要求 |

### 5.2 可见区、分页与选择

1. **计算可见卡片。** 图库按已有列宽和源图尺寸预计算每行最高卡片及累积高度。裁剪板按当前分组目标尺寸估算同组卡片高度。通过二分在行偏移中定位首尾，只挂载上下约一屏的预留区。若现有列式瀑布流的视觉顺序不同，则保留同一摆放算法，为每列维护各自的累计高度和可见窗口。用 `ResizeObserver` 合并真实高度校正，按帧刷新滚动状态。折叠分组和列数变化以 `(分组 ID, 资产 ID, 卡片内偏移)` 恢复锚点。
2. **独立保留状态。** 卡片状态按资产 ID 存，组件移出视口后可还原滚动、选中、草稿与保存状态。当前拖拽和键盘聚焦的卡片保持挂载到交互结束。裁剪卡现有 650 ms 延迟提交需要放到页面级调度，切页或窗口化卸载时按原有保存语义刷新或持久化草稿。长引导滚动中验证 Shift 选区、滑动勾选、键盘跨屏导航和返回锚点。
3. **稳定游标。** 查询输入包含筛选、排序及版本，游标包含规范化排序值与 `asset_id`。例如降序尺寸并按 ID 升序时，下一页边界为 `size < last_size OR (size = last_size AND id > last_id)`。处理空值、同值、升降序和现有指标回填的时序。列表使用轻量投影，避免每卡单独查询标注和集合。精确计数按筛选和数据版本复用，选择时做 ID 与筛选的交集计数。用 `EXPLAIN QUERY PLAN` 验证复合索引，并用项目真实筛选测开销。按可见窗口保留有限页数据，远处位置用锚点重新查询。
4. **跨页选区按快照执行。** 少量选择仍用 ID 集合。全选使用项目、筛选版本和排除 ID 表达，开始批量操作时由后端解析为稳定范围。同一范围用于预览、裁剪、回收、打标、提示词统计和导出，操作状态按任务追踪。取消重试与撤销必须沿用相同目标集。检查当前 `asset_summaries` 和 `asset_transform_plans` 的 5,000 条截取点，跨页命令需要分页或显式报超限，避免把部分结果显示成全量成功。 [`assets.rs`](../src-tauri/src/project/assets.rs#L359)、[`commands.rs`](../src-tauri/src/commands.rs#L1216)

### 5.3 大文件浏览、像素内存和磁盘缓存

| 使用场景 | 图像如何加载 |
| --- | --- |
| 网格、列表、打标素材条 | 使用 256 px JPEG 缩略图。保留原图／裁剪后两种语义。只有可见区和少量相邻视口设置 `src`，选中与聚焦优先。按源图或处理后尺寸预留布局，缩略图载入无需等待高画质。 |
| 裁剪板和检查器 | 先显示 256 px。裁剪板默认 512 或 768 px 代理，实际交互或检查器选中时按卡片物理像素、缩放需求和当前资源预算升级。裁剪计算始终基于 EXIF 归正后的原始坐标，代理只负责显示。 |
| 工作台、分割对比和去重复核 | 只为当前图片请求 1600 px 无损 WebP，保留 alpha、归正和色彩。高倍检查在用户停下缩放后再请求所需分辨率。若确需看 1:1 局部像素并且基准显示单张大图仍超预算，再增加视口分块，待切换时取消旧分块。 |
| 导出 | 在后台按已保存的裁剪配方和原始文件生成训练图，保持原尺寸、边界取整、透明处理、像素与标注格式的实际行为。页面预览分级与导出的训练尺寸各自独立。 |

- 分开限制**压缩文件字节数、解码像素数和可见位图内存**。例如 8,000×8,000 的一个 RGBA 缓冲约 244 MiB，后续归正、颜色转换、缩放和编码还可能同时持有额外缓冲。按解码前像素数、通道和缓冲副本数给任务预留字节。当前 80 MP 约束应用到所有会实际解码原图的入口，超大但有效的文件可按产品限制显示原因并允许重新选图或缩小外部副本。JPEG 继续使用降分辨率解码，透明 PNG 和 TIFF 按最坏的整图解码纳入预算。 [`worker/main.py`](../worker/main.py#L68)
- `op_display` 和不使用代理的渲染在读取后才限边。先测当前解码、EXIF、ICC、alpha 及编码各段，再决定采用原解码器的降分辨率路径，或按格式加入 libvips 等经过验证的预览解码后端。新后端以打包可用、视觉和几何一致为前提，保留测试夹具比较色彩、方向、透明边缘和导出像素。 [`worker/main.py`](../worker/main.py#L444)
- 同一版本的重复显示请求只生成一次。缓存键包含内容哈希、视图类型、尺寸档、渲染算法版本和涉及的配方版本，旧协议 URL 可映射到已有版本。落盘缓存按字节、最近访问和项目配额淘汰，初始可按每项目 1 GiB 或可用空间的一部分来测。锁定当前正在用的项，生成完成后原子重命名。空间不足时让用户继续看已有代理并给出清缓存入口。手动与自动清理范围仅包含可重建派生文件。
- 维护可见请求数量和预估字节的双限额。快速滚动、切图、隐藏页面或项目变化后，取消尚未执行的任务，并对完成的过期请求丢弃画面更新。必要时关闭临时 `ImageBitmap`、释放 Blob URL 和旧 canvas 引用。玻璃效果保留在固定导航与弹层。用 WebView2 实测识别高开销模糊层，减少大列表上随滚动更新的透明合成面。

对安装包内的脚本做了一次大文件基线测试。输入为 6144×4096、96.0 MiB 的合成 RGBA PNG，对 256 px 缩略图和 1600 px 大图分别启动独立进程并预热协议。缩略图首次生成约 **0.68 秒**，进程工作集峰值 **329 MiB**。大图约 **3.06 秒**，峰值 **265 MiB**。两次空闲进程工作集峰值均为约 41 MiB。使用 Python 3.13 与 Pillow 10.4.0。数值是单文件局部基线，包含实际编码写盘，另按第 5.4 节测试页面与多个进程共同加载的表现。

### 7.1 导入：一次源读取与暂存字节分析

- 复制模式在 [`import.rs`](../src-tauri/src/project/import.rs) 的 `prepare_one_inner` 中改为：复制到 `staging/import-<scanId>/<序号>.<ext>` 的同时计算 SHA-256 与字节数，读取前后核对长度和 mtime；随后用哈希执行重复判断，Pillow 直接分析这份暂存字节；成功后在同一卷内用 `rename` 不覆盖地发布为 `originals/<hash>.<ext>`。原先「完整 SHA-256 → 分析 → 再次完整读取并哈希复制」的两次完整源读取减为一次（`README`/`ACCEPTANCE` 中旧描述已不再适用）。
- 已存在的同名受管理原件按哈希确认一次，并在同一任务内缓存校验结果（`verified` 集合），避免 `keep` 策略下反复整读。发布过程中目标被并发创建时复用已验证对象；跨卷时回退为复制并校验。
- 引用模式只读取一次源文件计算哈希，分析前后各核对一次来源长度与 mtime；消失、被替换或变化按 `SOURCE_CHANGED` 报告。
- `worker/main.py` 将 80 MP 像素上限、静态帧数检查移到实际解码之前，并通过 `OpError` 透传 `TOO_LARGE` / `UNSUPPORTED_FORMAT`；Pillow 的 `DecompressionBombError` 也映射为 `TOO_LARGE`。缩略图、大图、渲染与导出入口共用同一像素上限。
- 未实现：除长度与 mtime 之外的文件身份识别（如 Windows file ID）；同名替换的极端场景仍以现有长度／时间戳契约为准。

### 7.2 导入：分批短事务与图库增量可见

- 并行线程只做复制、哈希、分析和缩略图，返回完整的 `PreparedAsset`；单一写入端在 `commit_prepared` 中按「首批 6 张、后续 24 张」组装一个短事务，逐行使用 savepoint 隔离失败，锁内按当前 `MAX(sort_index)` 连续分配顺序，并最终复核来源路径与内容哈希。
- 每批提交后发送节流的 `assets:import-committed` 事件，负载为 `projectId / jobId / commitSeq / committed / total`；首批与最后一批必发，其余至少间隔 300 ms。任务终态仍由现有 `assets:changed` 刷新项目总计、集合与任务中心。
- 前端 [`ProjectShell.tsx`](../src/app/ProjectShell.tsx) 新增 `librarySignal`，只分发给图库；[`LibraryPage.tsx`](../src/features/library/LibraryPage.tsx) 以 250 ms 合并多次提交，空图库走首屏查询，已有内容重查可见窗口。`refreshLoaded` 合并旧尾部时按 ID 去重，避免新记录插入后出现重复卡片。
- 最终生效的 `collectionId` 随扫描文件与任务输入一起持久化，重试沿用原分组；`import_scan` 的目录遍历与文件头读取移入 `spawn_blocking`。
- 未实现：第 2.2.5 节的逐候选检查点与崩溃后自动补齐；当前仍以「已提交记录 + 来源路径去重 + 显式重试」恢复。同任务内被哈希占位跳过的候选若首张失败，需要一次失败重试才会重新导入（重试会重新读取扫描文件）。

### 7.3 去重与图片协议

- [`quality.rs`](../src-tauri/src/project/quality.rs) 的 `dedupe_scan` 只在短锁内读取候选快照、有效阈值与回收区数量，分组计算在锁外完成；`build_group_ids` 同时服务完整扫描与 `dedupe_summary`，保持原有精确／近似分组和推荐保留语义。
- `dedupe_summary` 新增轻量指纹 `COUNT(*) / SUM(revision) / MAX(sort_index) / 回收区数量`。命令层按 `(项目, 指纹, 阈值)` 缓存摘要；导入提交、状态修改、回收与恢复都会改变指纹。扫描与摘要都放入阻塞线程。
- 图片协议改为 `register_asynchronous_uri_scheme_protocol`，在 `spawn_blocking` 中查库与生成；以 `(项目, 资产, 变体, 版本)` 合并并发请求，先写临时文件再原子替换缓存文件；`ImageGate` 限制同时等待生成的请求数，未命中时仍沿用 256 px 缩略图与 1600 px WebP 语义。
- 图像工作进程池增加交互／后台两条等待通道：缩略图、大图、裁剪预览使用交互优先级，导入分析、指标回填与导出渲染使用后台优先级，避免导入期间切换图片长时间排队。

### 7.4 运行时就绪与验证

- `WorkerPool` 记录是否已通过真实操作验证；`app_info.workerReady` 仅在成功执行过一次图像操作后为 true。前端启动后主动 ping 一次，设置页可看到实际 Python 与 Pillow 版本，缺少运行时时在导入前显示具体错误。
- 已执行：`cargo check --offline`、`cargo test --offline`（19 通过、2 忽略，新增批次写入、锁内去重新增与游标分页用例）、`npm run typecheck`、`npm run build`；直接调用 `worker/main.py` 验证分析并生成 256 px 缩略图、10,000×10,000 伪 PNG 被 `TOO_LARGE` 拒绝、RGBA 图的缩略图／WebP 大图／PNG 渲染输出正常。
- 未执行：第 4 节的应用内 1,000／5,000 张基准与第 5.4 节大库验收、第 6.2 节的干净机安装矩阵；第 3 节由基准决定的第二批优化（大 PNG 代理复用、指标延后计算）留待有基准数据后推进。

### 7.5 大库页面与发布资源（第二轮）

- 图库网格在超过 240 张后启用视口行窗口化：按列宽与源图比例预估每行高度，二分定位可见行，只挂载视口上下各约两行；卡片标注区固定为两行高度，使行高可预测。图库恢复活动状态时按筛选是否变化选择首屏或窗口刷新，隐藏页面不再查询与预取。
- 裁剪板改为渐进加载（每批 200 张摘要与配方，首批立即呈现）；超过 48 张的分组默认折叠，只显示组名、数量与目标尺寸，工作台当前图片所在组自动展开；分组归属改为一次建立索引，避免逐资产扫描成员。卡片默认使用 256 px 原图缩略图，拖动、滚轮或选中后才请求 1600 px WebP 并淡入。「应用尺寸到分组」在折叠或尚未加载完时按完整成员集合解析后再执行。
- 图库深页改为稳定游标：[`assets_query`](../src-tauri/src/project/assets.rs) 接受上一页最后一张 ID，按当前排序表达式与 `a.id` 续页，避免 `LIMIT/OFFSET` 深扫；游标行消失时前端回退到偏移分页，追加时按 ID 去重。新增游标与偏移顺序一致、同值排序不重复的单元测试。
- 图库去重的分组列表与回收区各自显示前 60 项并可继续加载；组内成员保持原有 40 张展开语义。质检页同一规则的问题先显示前 100 条并可继续加载。
- 发布构建不再探测构建机的仓库脚本、`wd14Tagger` 内嵌 Python 与 `C:\Python3xx`；`worker/main.py` 优先从安装资源目录加载，开发机候选仅在 debug 构建启用。WD14 改用设置中的 Python（`YOYOKU_PYTHON` 次之），与基础图像进程共享配置；Florence 同样支持该环境变量。
- NSIS 资源从「递归收集 `worker/`」改为显式列出 `main.py`、`translate.py` 与三个模型适配脚本，避免把 `__pycache__` 等构建机缓存带入安装包。
- 未实现：裁剪板的逐行视口虚拟化（当前以分组折叠 + 低清代理控制 DOM 与解码）；跨页选区仍以 ID 集合与全量 ID 预取表达，未改为筛选版本快照；WD14／Florence 独立运行库路径与模型最小推理自检；第 6.2 节的干净机安装、升级、卸载矩阵仍未执行。
